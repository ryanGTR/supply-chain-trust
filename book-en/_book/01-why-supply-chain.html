1  Opening: The Attack Does Not Come Through the Front Door

Java engineers everywhere remember one Friday in December 2021. A vulnerability called Log4Shell (CVE-2021-44228) went public: log4j — the logging library so ubiquitous that nobody remembers adopting it — could be made to perform a JNDI lookup, fetch remote code, and execute it, simply by logging one attacker-controlled string.

That weekend looked much the same inside any typical banking environment: everyone tearing through every system to answer a question that sounds trivial — “where exactly are we using log4j?”

And finding they could not answer it. Not out of laziness, but because no inventory existed recording which dependencies, at which versions, each system had pulled in. log4j usually is not something you added directly; it arrives as a dependency of a dependency of a dependency (a transitive dependency). Your pom.xml is spotless, and your WAR file contains three different versions of log4j-core.

That is where this book starts: modern attacks do not come in through the code you wrote. They come in through the code you brought in.

1.1 Three cases, three ways in

Predict first: if you were the attacker and wanted malicious code running inside a bank’s data centre, which route would you take? Straight at the firewall? Phish a VPN credential? Hold on to your answer and check it against the three real cases below.

1.1.1 Log4Shell: nobody poisoned the well — everyone was drinking from the same one

Strictly speaking Log4Shell was not a supply-chain attack. Nobody planted a backdoor; an honestly intended feature turned out to be a vulnerability. But it exposed the first layer of the supply-chain problem: you do not know what you depend on. When a flaw lands in a shared component, the blast radius is “every system that uses it” — and you do not even have the list.

1.1.2 xz-utils: three years undercover, and it nearly reached every Linux machine

In March 2024, xz-utils — the compression library installed on essentially every Linux system — was found to contain a backdoor (CVE-2024-3094). This time someone really did poison the well, and the method was chilling: an account under the alias “Jia Tan” spent roughly three years contributing to the project, earning trust, and becoming a maintainer, then hid a carefully disguised backdoor in the released tarball. The backdoor was not in the git source at all — only in the packaged release — and its purpose was to hook liblzma into sshd and open a hole during SSH authentication. It had already reached the testing branches of several distributions and was weeks away from broad rollout. The reason it was caught reads like fiction: one engineer noticed SSH logins had become about 500 milliseconds slower, and pulled on the thread.

That exposed the second layer: “open source, widely used, actively maintained” does not mean trustworthy. Trust rests on people, and people can be cultivated over years.

1.1.3 Malicious npm packages: going straight for the water supply

Attacks in the npm ecosystem are routine: typosquatting (registering loadsh for people who mistype lodash), dependency confusion (hijacking an internal package name with a public one), or the 2018 event-stream incident — the original maintainer, unable to keep going, handed the package to a helpful stranger, and the helpful stranger added code that stole from specific cryptocurrency wallets. A package with millions of weekly downloads changed maintainers, which means it changed trust level, and not one downstream user was notified.

That exposed the third layer: every npm install and mvn package you run is, in essence, pulling code a stranger uploaded moments ago straight into your build — and almost nothing on that path is verified.

Back to your prediction. Why would an attacker bother with your firewall? Come in through a dependency and you will build them into the system yourself, then sign it off into production. The front door has a guard. The back door you opened yourself.

1.2 Six attack surfaces: every step from source to production is a target

Lay out how software travels from an engineer’s hands to production, and every link is a surface:

Attack surface Example technique The trust question underneath
① Source Stolen developer account, malicious pull request, long-game infiltration (the social side of xz) Did this person really write this code?
② Build Poisoning the build server — the SolarWinds route, where the artifact was backdoored and then officially signed Is the build output a faithful translation of the source?
③ Artifact Released tarball differs from git contents (the technical side of xz); artifact store swapped Is the file I received the one that was built?
④ Feed / Registry Typosquatting, dependency confusion, maintainer handover (event-stream) Who is behind this package name today?
⑤ Deploy Pipeline substitutes the image; tag drift (the same tag pointing at different content) Is what went live the thing that was tested and approved?
⑥ Production Runtime auto-update fetches a malicious version Is the thing running still the thing I verified?

Notice something: all six questions collapse into one sentence —

“Is the thing in my hands the same thing that someone I trust made?”

That sentence is the question this whole book answers. And the tools that answer it are not firewalls or WAFs. They are three old cryptographic primitives: hashes, digital signatures, and MACs.

1.3 Roadmap

Part I does not rush into supply chains. It lays the foundation first:

  • Chapter 2 — Digital signatures. What “sign with the private key, verify with the public key” actually guarantees, and why we sign a hash rather than the message. Comes with an experiment you can run: sign a file, change one byte, watch verification fail.
  • Chapter 3 — PKI and chains of trust. Signatures need a public key to verify against — but why is that key trustworthy? Certificates, chains, and the conclusion people repeat until it stops landing: the end of the chain is not mathematics, it is a human decision.
  • Chapter 4 — Authenticated encryption (deep dive, skippable). When you combine signing and encryption, both intuitive orderings have holes. MACs, Encrypt-then-MAC, AEAD.
  • Chapter 5 — The capability boundaries of the three primitives. A table of what hashes, signatures, and MACs each give you and each refuse to give you, with the six attack surfaces mapped onto “which primitive can stop this, and which cannot”. That table is the map for Part II.

Part II takes the primitives to the factory floor: the requirements in NIST’s SSDF, artifact signing and promotion, and key custody — including what I could not make work and what I got wrong the first time. Part III turns to what comes in: dependencies, SBOMs, and what trusting a package actually commits you to.

1.4 Honest boundaries

ImportantOne last alignment before we start

Every case in this chapter is drawn from public reporting and public technical analysis; the original disclosures are authoritative on detail. Environments described in this book are de-identified reconstructions of “a typical banking environment” and correspond to no real institution. This book is my learning and implementation record — what it can give you is a mental model and experiments you can rerun, not a compliance endorsement.

What to take away: the modern attack surface is the code you bring in; there are six places to strike between source and production; and all six reduce to one question — “is the thing in my hands the thing the person I trust actually made?” The next chapter starts with the first building block that can answer it: the digital signature.
